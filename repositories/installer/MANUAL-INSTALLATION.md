# Manual installation planning runbook

Phase 0 does not provide a production-ready IbisPanel release or deploy anything. This describes the manual workflow that a future installer must preserve. Follow the locked source and the [development prerequisites](https://github.com/IbisPanel/docs/blob/main/development-setup.md) when preparing an isolated Linux environment. Consult the [official baseline guide](https://docs.pterodactyl.io/v2/panel/getting-started) for inherited service configuration; do not assume its upstream binary URLs are IbisPanel releases.

1. Choose compatible Linux hosts for Panel and Wings. Record source pins, architecture, intended paths, ports, DNS, proxy/TLS topology, runtime versions and service identities. Inspect existing installations first. For existing systems, take a verified recoverable backup before any change.
2. Prepare PHP/FPM and extensions, Composer 2, MySQL/MariaDB, Redis and a web server. Serve Panel only from `public`. The source requires building assets with Node >=22.12 and the npm lockfile. Use the original dependencies without updating locks.
3. Obtain reviewed source at the exact pins and verify it. In a dedicated Panel directory install Composer dependencies and run `npm ci` plus the inherited build. A source checkout does not include a production-validated built release. Inspect lifecycle hooks before execution.
4. Create a new restricted application database and environment configuration. Generate an encryption key only for a new installation, store a protected off-host copy, and configure URL, DB, Redis, sessions, queues and mail. Use interactive secret input; never include real secrets in docs or command logs.
5. Against the fresh database only, apply the inherited schema/seeds and create the first administrator. Configure the inherited queue worker and scheduler, filesystem ownership and TLS web entry point. Check login, authorization, queued jobs and scheduling before opening public access.
6. On each node, prepare compatible Docker and Linux prerequisites. Build or obtain the pinned Wings daemon, preserve its inherited module/config conventions, register the node in Panel and transfer config securely. Configure its service, TLS/proxy and narrowly scoped required ports. Keep node tokens private.
7. Validate the paired Panel/Wings APIs, console, files, SFTP, allocation behavior, schedules and backup/restore with disposable workloads. Confirm startup after reboot and verify that web and daemon credentials do not appear in logs.
8. Record versions, checks and backup/recovery procedures. Keep a matching code/DB/environment/config rollback checkpoint for future updates. Stop on failed health checks rather than reopening service with unknown state.

Manual updates preserve APP_KEY, environments, storage, customizations and workload files; they require staged compatible code, quiesced writers, a DB checkpoint and worker restarts. Manual migration follows the separate Migration Hub plan and must not replay arbitrary source database migrations against a different target schema. Diagnosis is observational until an operator selects a specific repair.

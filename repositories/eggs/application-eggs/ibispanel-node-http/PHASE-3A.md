# Phase 3A validation — private Node.js HTTP hosting

Date: 2026-11-03. Development node: `ibis-wsl-node-01` in Ubuntu 24.04 WSL2. Panel and Wings source were not changed.

## Existing Egg audit

The Eggs repository contains `generic-eggs/nodejs` and `generic-eggs/nodemon`, plus Node-based application-specific Eggs such as Haste Server, Uptime Kuma, and several bot/game Eggs. Haste Server uses Node 18 (end of life); Uptime Kuma and the bot Eggs install their own upstream applications rather than a user-uploaded dependency-free HTTP fixture. Nodemon installs packages at startup and is aimed at development bots. The generic Node.js Egg offers a Node 24 yolk and user-upload mode, but its quoted `"*.js"` startup comparison routes `.js` files to `ts-node`; its install path updates packages and supports remote repository cloning. Its README also requires a per-app startup detection change. None fits a fixed, no-download HTTP test without configuration or behavior changes. Their original files and author fields remain untouched.

Node.js 24 is an active LTS line. The existing generic Egg's `ghcr.io/ptero-eggs/yolks:nodejs_24` image was checked and contained Node 24.17.0. The official `node:24.22.2-bookworm-slim` image was checked and contained Node 24.22.2, but its standard Docker entrypoint opened a Node REPL under Wings instead of running the Egg startup command. The narrowly scoped local Dockerfile pins that official image by digest and provides a fixed Node entrypoint. No package installation or remote application script runs when this Egg installs.

## Observed validation

- Imported the Egg through the real admin UI. The server creation API returned HTTP 201. Its no-download install script completed, and the files were uploaded through the Panel file manager (both uploads returned HTTP 200). Files were owned by the `pterodactyl` server user.
- The initial unadapted official Node image entered a REPL, so HTTP failed. The failed disposable container was stopped, the local adapter image was built, and this server's image was updated through the admin UI. The server then started the application successfully. No upstream Egg or Panel/Wings code was modified.
- Actual container entrypoint: `/usr/local/bin/node /home/container/index.js`; `node --version` returned `v24.22.2`. `GET /` returned HTTP 200 and the expected text from both WSL and Windows via the private IP. Requests appeared in the live console. Browser WebSocket authentication succeeded.
- Panel restart produced `running → stopping → offline → starting → running`, with application shutdown and startup logs. A separate Stop produced `running → stopping → offline`; its Docker container exited and port 64739 stopped listening. A separate Start restored HTTP 200.
- The Panel file editor showed `message.txt`; editing and saving it changed the HTTP response. Reloading the editor and restarting the container preserved the edited text. The dashboard still listed the server and its configuration.
- Client UI reported CPU, memory, network, container uptime, and disk use. Disk showed about 1.27 KiB for the two fixture files; actual volume blocks were about 12 KiB. Docker stats showed about 12–14 MiB live memory against an approximately 294.4 MiB enforced cap, and Docker CPU quota was 25,000 / 100,000. The container was not privileged.
- Docker inspection showed host binding `172.20.175.81:64739` for TCP and UDP. Wings API and SFTP stayed on WSL loopback; Docker's remote TCP API was absent. Windows had no host listener or port proxy for 64739. WSL NAT is not a complete security boundary, so this allocation must stay private and be rechecked after WSL restart.
- Wings and Docker were active at final check, recent Wings warning journal entries were absent, `/etc/pterodactyl/config.yml` remained `0600 root:root`, and the Docker socket remained `0660 root:docker`. No credentials or node tokens are stored here.

See the README for exact local restart and WSL IP recovery steps. Phase 3B recommendation: audit the existing generic Discord/bot Eggs and choose a current supported Node runtime; use a separate bot Egg with narrowly validated startup variables and local file upload, then test a token-free mock bot before adding any real credential through the Panel's protected secret mechanism. No Discord bot work was started here.

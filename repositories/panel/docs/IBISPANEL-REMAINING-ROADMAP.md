# IbisPanel remaining roadmap

Date: 2026-11-07. Priorities are evidence-based gates, not delivery promises. The [project report](IBISPANEL-COMPLETE-PROJECT-REPORT.md) records the current implementation and repository evidence. Do not resume the withdrawn M1 Software page/planner without a fresh design.

| Priority / proposed milestone | Work and reason | Dependencies | Testable acceptance |
| --- | --- | --- | --- |
| P0 — Runtime safety audit | Review Git import SSRF/archive/path handling, file permissions, startup command trust, credentials and container boundaries before wider access. | Existing importer and Panel/Wings auth | Negative fixtures reject traversal, unsafe URLs and unauthorized imports; no secrets in logs/history |
| P0 — Backup and recovery proof | Verify server volumes, Panel DB/APP_KEY, node configuration and rollback together to prevent data loss. | Isolated restore target and documented ownership | A disposable server and account are restored from a captured set, with matching hashes and working login |
| P0 — Queue supervision/recovery | Make worker availability, stalled content jobs and notifications operationally visible without blindly replaying old jobs. | Existing isolated Minecraft queue, Redis | Fresh job completes under supervised worker; interruption/retry and stale-job handling are deterministic |
| P1 — Node.js app lifecycle | Turn the manual import/npm/build/start sequence into an explicit, safe, observable deployment flow. | HTTP Egg, private URL action, resource limits | New disposable app installs/builds/starts/restarts/stops with truthful Wings states, logs and preserved files |
| P1 — Public HTTP routing | Define verified domain mapping, TLS, proxy and reachability instead of inferring them from allocations. | Node security and ownership checks | Owned domain serves HTTPS, private allocations remain labeled private, bad/wildcard addresses never become links |
| P1 — Workload matrix | Validate representative Minecraft Java/Bedrock, bot, Python, static and other Eggs individually. | Pinned images, resource budget, safe fixtures | Each claimed workload passes provision, start, network/console, stop and deletion checks; unsupported ones are marked unverified |
| P1 — Process-state regression | Add integration coverage for failed startup, timeout, WebSocket loss and restart with the Node HTTP Egg; capture fresh HTTP and port ownership if STOP is reported to leave a site live. | Wings state fixtures and scoped Egg marker | UI never reports Connected for offline process; state transitions follow Wings; STOP ends the container and releases its listener across repeated cycles |
| P2 — Minecraft suite | Re-plan safe software/version changes, datapacks, modpacks, players, presets and server-icon flow. | Compatibility evidence, backup/rollback, supervised content queue | Each feature has Egg-specific permissions, destructive-change preview, real disposable-server trial and recovery test |
| P2 — Provider and UX completeness | Finish language coverage, visual/accessibility matrix and image/branding administration. | Four modes and editor | Key pages usable at desktop/mobile with keyboard/screen reader; save/reset/upload checked in all modes |
| P2 — Installer | Implement read-only discovery/preflight/plan first, then selected Panel/Wings/update/repair operations. | Pinned release artifacts and recovery proof | Clean install and interrupted upgrade resume in disposable hosts without regenerating existing secrets |
| P2 — Migration Hub | Build versioned read-only profiles before any write adapter for Pterodactyl, Reviactyl, Pelican or PufferPanel. | Source fixtures and destination recovery | Unsupported fields and conflicts reported; staged test migration preserves source and has a verified rollback |
| P3 — Git automation | Consider private repositories, pull/update, webhooks and CI/CD only with scoped credentials and rollback. | P0 security audit and P1 app lifecycle | Authorized updates are pinned/reviewable, reversible and do not expose credentials |
| P3 — Broader platform/release | Publish maintained images, compatibility matrix, CI, security update policy and public release documentation. | Proven workloads, recovery and public routing | Reproducible signed/pinned release passes supported OS/runtime matrix and security review |

Near-term order: complete P0 gates, then the Node.js lifecycle and public-routing design, then broaden workload claims. The installer and migrator remain design-only until their own recovery prerequisites are proven.
